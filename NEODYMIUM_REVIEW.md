# Пересмотр интеграции Neodymium

Проверены локальные исходники FalseTweaks 3.9.7, текущий порт 4.x и
Neodymium Unofficial 0.4.3. Этот документ описывает изменения в коде,
а не подтверждённый прирост FPS в DF4.

## Что в оригинале отличалось

| Участок | FalseTweaks 3.9.7 | Текущая интеграция после переработки |
| --- | --- | --- |
| Построение геометрии | Консервативное разделение безопасных/небезопасных блоков; отдельный экспериментальный прямой путь ChunkMesh | Разделение сохранено; обычные Forge/Neodymium вызовы на главном потоке |
| Планирование | Собственный OcclusionRenderer управлял очередью и обновлениями | Асинхронная очередь с бюджетом главного потока; ожидания рабочих потоков в цикле кадра нет |
| Отсечение за препятствиями | Собственный модуль occlusion, пространственное хранилище, видимость секций и сущностей | Этот модуль **не перенесён**; остаются проверки видимости/фрустума и возможности самого Neodymium |
| Тени | Отдельное ограничение области отбрасывающих тени секций | Мост к Neodymium; сбор регионов после обновления списка, консервативный fallback при отсутствии данных |
| OptiFine | Ограничения конфликтующих настроек | Ограничения включаются по наличию Neodymium + OptiFine независимо от числа потоков |
| Прозрачность | Сортировка и специальные пути экспериментального режима | Сортировка объединённого результата на главном потоке; лишняя сортировка половины геометрии удалена |

Экспериментальный режим 3.9.7 сам предупреждает о мерцании MicroBlocks,
ProjectRed и Mekanism. Он не является безопасной заменой текущего пути для
всех модифицированных блоков. Перенос occlusion требует собственного этапа
реализации и визуальных проверок; настройки старого раздела `occlusion`
в файле 4.x его не включают.

## Исправленные расходы и ошибки

* Старый scheduler возвращал false до опустошения очередей. Ванильный
  EntityRenderer повторяет updateRenderers в цикле до дедлайна кадра.
  Асинхронный scheduler теперь завершает работу за текущий кадр сразу
  после отправки/приёма доступных задач.
* Вместо полного сортирования очереди выбирается короткий список ближайших
  секций с приоритетом находящихся в поле зрения. В работе не более двух
  задач на поток. Очередь очищается одним проходом без повторного поиска
  каждого завершённого renderer и сдвигов середины списка.
* Для CompactArrayList добавлен прямой интерфейс. Reflection остаётся
  запасным вариантом для отличающихся реализаций, а не вызывается для
  каждого элемента очереди в обычном OptiFine.
* Главный поток получает бюджет `threading.neodymiumMainThreadBudgetMs`,
  по умолчанию 2 мс. Одна сборка/выгрузка геометрии неделима и может
  превысить бюджет. Это не гарантия максимального времени кадра.
* Удалена сортировка прозрачной геометрии на рабочем потоке: сразу после
  объединения она всё равно сортировалась снова, включая построение BSP.
* Каждая задача теперь владеет собственными координатами, кешем и
  результатом. Каждая сессия владеет своими очередями. Поток старого мира
  не может опубликовать результат в новую очередь. Ожидание join на
  главном потоке удалено; выгрузка мира явно закрывает сессию.
* Повторное изменение уже dirty-секции инвалидирует снимок. Ванильный
  markBlocksForUpdate в этом случае повторно markDirty не вызывает.
* Сбой рабочего потока и частые изменения секции приводят к обычной
  сборке на главном потоке вместо бесконечной отправки той же задачи.
* Главный поток пропускает только координаты, обработанные в конкретном
  проходе конкретной задачи. Изменение глобальной классификации renderType
  другим потоком больше не приводит к дублированию геометрии.
* При изменении секции во время commit текущая геометрия объединяется до
  конца, затем назначается новая сборка. Дополнительный проход для камеры
  внутри блока не отменяется.
* Сбор статистики Neodymium по всем секциям выполняется только при открытом
  F3. Сбор получателей теней перенесён после обновления loadedRegionsList.

## Что нельзя заключить из конфига

OptiFine DynamicLights в этой интеграции перенаправляется на FalseTweaks
DynamicLightsDrivers.frontend. Две включённые настройки не доказывают, что
одновременно работают две независимые системы освещения. Движущиеся
источники света всё же могут вызывать частые перестройки секций.

Успешная загрузка миксинов, наличие двух потоков и успешная сборка jar
не доказывают улучшение FPS. Также восстановление многопоточности не
означает восстановление всей системы видимости из 3.9.7.

## Проверка результата

`gradlew test` проверяет бюджет приёма результатов, повторное изменение
во время commit, повторное использование renderer, изоляцию устаревшего
результата, закрытие сессии, отмену без голодания, уплотнение списка и
маску геометрии по проходам. Эти тесты не проверяют OpenGL и модовые ISBRH.

В F3 добавлена строка `FT chunks`: число задач в работе, завершённых и
отменённых задач, ошибок с переходом на обычную сборку и среднее время
главного потока в scheduler. Счётчики обновляются примерно раз в секунду.
`main` не включает остальной рендер Neodymium, GPU и другие моды.

Для измерения в DF4 нужны одинаковые мир, положение, направление камеры,
дальность, ресурспак, погода и ограничитель FPS. Сравнивать отдельно:

1. Неподвижный вид после прогрева: FPS/время кадра, строка FT chunks.
2. Движение по одинаковому маршруту: время кадра и скорость прогрузки.
3. Перезагрузка чанков и переход между мирами: отсутствие пропавших секций.
4. Вода/стекло, модовые блоки и камера внутри блока: визуальная корректность.

Нужно сравнить сборку до изменений и после, а также Neodymium с отключённой
многопоточностью. Измерения в тестовом мире без модов не заменяют замеры DF4.
